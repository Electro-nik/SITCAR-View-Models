Як рахувалась вартість

Ці тести виконувалися для одного однакового ORG-промпта по ТЗ SITCAR. У моделі передавалися лише відповіді користувача з форми — без завантажених файлів. Тому блок «1 ORG-промпт» показує вартість саме одного такого API-запиту, а не повного проходження SITCAR. Окремо показано фактичне споживання токенів і теоретичний сценарій, якщо output дійде до заявленого максимуму моделі.

Скрипт перевірив збережений Prompt sent to model: у всіх знайдених HTML він однаковий.

1 ORG-промпт · фактична вартість Реальна вартість одного API-запиту ORG за фактично використаними input/output tokens, плюс прогнозований податок / націнка. Файли в цьому тесті не передавались.
1 ORG-промпт · верхня оцінка Той самий фактичний input ORG, але output умовно дорівнює повному заявленому Max output моделі, плюс податок. Це теоретична верхня оцінка, а не фактичне споживання.
Безплатна версія · фактичний сценарій Фактична вартість ORG з податком × 3
Повна версія · фактичний сценарій Фактична вартість ORG з податком × 10. Це прогнозний множник для повного пакета: 9 промптів + 1 презентація; фактична вартість інших модулів може відрізнятися від ORG.
Безплатна версія · MAX сценарій Верхня оцінка ORG з податком × 3
Повна версія · MAX сценарій Верхня оцінка ORG з податком × 10

Важливі уточнення

  • На вхід ми знаємо фактичну кількість input tokens, оскільки її повернув API конкретної моделі. Різні моделі можуть токенізувати один і той самий текст трохи по-різному.
  • На виході неможливо заздалегідь точно сказати, скільки токенів використає модель.
  • Під час цих тестів у модель передавалися відповіді з форми без файлів, а відповідь генерувалася без ручного обмеження максимальної кількості output tokens. Тому фактичний Output tokens — це стільки, скільки модель реально використала до завершення відповіді.
  • Колонка ORG при MAX output — це теоретична верхня оцінка одного ORG-промпта: поточний фактичний input залишається таким самим, а output вважається рівним повному заявленому Max output. Це не означає, що модель зазвичай витратить стільки токенів.
  • Max context / input* — це заявлений Context window із HTML. У частини API context window є спільним лімітом для input + output, тому його не слід завжди трактувати як гарантовану можливість одночасно використати весь context для input і весь Max output.
  • Прогноз MAX рахується лінійно за тарифом Output price / 1M, записаним у конкретному HTML. Якщо провайдер має додаткові тарифні рівні, long-context pricing або інші правила, реальний рахунок може відрізнятися.
  • Податки в цій таблиці є прогнозними налаштуваннями скрипта: OpenAI 20% · DeepSeek/OpenRouter 16% · Gemini 20% · Claude 20%. Їх можна змінити у словнику TAX_RATES.
  • Повторних запусків приховано: 1. Для кожної моделі використовується найновіший HTML.
Prompt ORG, який відправлявся моделям 
Роль: ти — ШІ-аналітик SITCAR System. Проаналізуй відповіді менеджера в цьому розділі та сформуй зрозумілий діагноз для власника / керівника / менеджера. Людина не знає методику SITCAR, тому пиши управлінською мовою без внутрішнього жаргону.
Вхідні дані користувача наведено наприкінці цього запиту.
Фокус аналізу:
Побудуй Паспорт організації. Не оцінюй менеджера. Оціни якість контексту, повноту даних, ключові прогалини, суперечності, ризики для подальшої діагностики.
Виміри оцінювання:
Для ORG оцінюй context_quality_оцінку 0–100, але не роби висновок про ефективність організації. ORG є базою для інших модулів.
Правила:
1. Використовуй тільки відповіді та завантажені документи. Не вигадуй фактів.
2. Відокремлюй факти, припущення, суперечності та прогалини даних.
3. Відсутність даних знижує рівень упевненості, але не автоматично оцінка.
4. Для кожного важливого висновку дай коротке пояснення «чому».
5. Не давай більше 5 рекомендацій. Рекомендації мають бути конкретними: дія, причина, очікуваний результат, відповідальна роль, строк.
6. Якщо даних недостатньо, поверни обмежений результат і список уточнень.
